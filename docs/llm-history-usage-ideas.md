# LLM が過去履歴を取得・有効活用しやすくする案

現状、セッション履歴は「直近 N 件＋予算」でコンテキストに載り、それより前は `history_get` / `history_search` ツールで取得する設計。以下は、LLM が過去履歴をより取り出しやすく・使いやすくするための案（優先度・工数は目安）。

---

## 1. 履歴ツールを part_* 対応する（推奨・中工数）

**現状**: `history_get` / `history_search` は manifest がある場合は manifest + reviewed/ を、無い場合は **reviewed/ のみ** を参照。leakscan 無し（PartSessionStorage）のセッションでは **part_* しか無い** ため、ツールは実質空になる。

**案**: manifest も reviewed/ も無い場合に **part_* を走査** するフォールバックを追加する。

- `history_get`: part_* をファイル名でソートし、`after_id` / `before_id` は part の ID（例: `part_001_user.txt` → `001`）で絞り込み、`limit` 件返す。
- `history_search`: part_* の内容に対して部分一致検索し、ヒットしたメッセージを返す。

**効果**: leakscan が無い環境でも、LLM が「過去のユーザー発言」「以前の自分の返答」をツールで取り出せる。長いセッションでコンテキストから外れた部分を必要な時だけ取得できる。

---

## 2. システムプロンプトでツールの使い方を案内する（低工数）

**案**: デフォルトの system instruction やモード設定に、履歴ツールの存在と使い方の一文を入れる。

例:
- 「必要に応じて `history_get` で過去メッセージを、`history_search` でキーワード検索して参照できます。」
- 「現在のコンテキストに含まれていない過去のやりとりが必要なら、`history_search` にキーワードを指定して検索してください。」

**効果**: モデルがツールを呼ぶ判断をしやすくなり、コンテキスト外の履歴を自発的に取りにいきやすくなる。

---

## 3. セッション要約をコンテキストに載せる（中〜大工数）

**現状**: compaction で古いメッセージを要約したテキストは manifest 経由の履歴ビューに「1 件の assistant メッセージ」として含まれる。leakscan 無しでは compaction も無い。また、セッション全体の「何をしたか」要約は self-improve でメモリに抽出されるが、**次のターンの初期コンテキストには載らない**。

**案**:
- **A) セッション要約ファイルを読んで先頭に付与**: セッション dir に `session_summary.txt` 等があれば、コンテキスト先頭（system の次など）に「Previous context summary: ...」として 1 メッセージ追加する。要約は別途生成（例: クエリ終了時の self-improve の副産物、または専用ジョブ）して書き込む。
- **B) compaction 要約を Part のみセッションでも利用**: leakscan 無しでも、一定ターンごとに「直近 N 件を要約したテキスト」を生成し、次回以降のコンテキスト先頭に 1 件だけ載せる。実装はコンパクション戦略の簡易版や、LLM 要約 1 回呼び出しなど。

**効果**: ウィンドウ外の内容を「要約 1 ブロック」で把握でき、何についての会話か・どこまで決まったかが LLM に伝わりやすくなる。

---

## 4. history_get の返却に「範囲の説明」を付ける（低工数）

**案**: `history_get` のレスポンスに、`"context": "Returned messages 001..020 (oldest..newest in session)"` のようなメタ情報を 1 フィールド追加する。あるいは `total_in_session` のような件数情報を返す。

**効果**: モデルが「まだ古い方がある／もう全部見た」を判断しやすくなり、必要に応じて `after_id` でさらに遡る呼び出しをしやすくなる。

---

## 5. 履歴要約ツールを追加する（大工数）

**案**: 新ツール `history_summary` を追加する。

- 入力: オプションで `from_id` / `to_id` や件数上限。
- 動作: 指定範囲（またはセッション全体）のメッセージを取得し、**LLM に要約させる**（既存の LlmCompletion 等を利用）。要約結果をツールの戻り値として返す。
- 代替: 要約は事前計算してセッション dir にキャッシュし、ツールはそのキャッシュを返すだけにする。

**効果**: 「このセッションで何が話されたか」を長文ではなく短い要約で取得でき、コンテキストを節約しつつ過去を活用できる。

---

## 6. コンテキスト構築を「要約＋末尾」の二層にする（大工数）

**現状**: TailWindowReducer が「末尾から max_messages / max_chars まで」を 1 本の履歴にしている。

**案**: 予算の一部を「古い部分の要約 1 件」に充て、残りを「直近の生メッセージ」に使う。

- 例: 予算 40 件のうち 1 件を「それより前の要約」、39 件を従来どおり末尾から取得。
- 要約は前回ターン終了時や、コンテキスト構築時に「ウィンドウ外」を 1 回要約してキャッシュする方式が現実的。

**効果**: 毎ターン、LLM は「昔の要約＋直近の流れ」を見られるため、長いセッションでもテーマや経緯を失いにくい。

---

## まとめ（優先度の目安）

| 案 | 効果 | 工数 | 備考 |
|----|------|------|------|
| 1. part_* 対応 | ツールが無い環境でも履歴取得可能 | 中 | leakscan 無しでも history_get/search が使える |
| 2. プロンプト案内 | ツール利用の動機づけ | 低 | 既存ツールの活用率向上 |
| 3. セッション要約の付与 | ウィンドウ外を要約で把握 | 中〜大 | 要約生成・保存の設計が必要 |
| 4. history_get のメタ情報 | ページネーション判断がしやすい | 低 | 既存ツールの UX 向上 |
| 5. history_summary ツール | 範囲指定で要約取得 | 大 | 新ツール＋要約パイプライン |
| 6. 二層コンテキスト | 要約＋末尾で常に「昔＋最近」 | 大 | Reducer/コンテキスト構築の変更 |

まずは **1（part_* 対応）** と **2（プロンプト案内）** から着手すると、変更範囲が限定的で、LLM の履歴活用がすぐに改善しやすい。
